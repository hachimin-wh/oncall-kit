# oncall-kit：agent 引擎如何使用与复用

> 结论先行：**可行，且工作量在"接线"不在"改写"。** oncall-kit 没有运行时代码，全部资产是引擎无关的 markdown；状态全部外置在 git 文件里，不依赖任何平台的隐藏状态。本地 Claude Code 是零适配路径（它就是 kit 的原生宿主之一）；任何通用 agent 框架只要补上触发、工具、技能装载三个薄层，就能执行同一套文件。

## 1. 为什么引擎无关

四个结构性原因，都来自 kit 自身的设计：

1. **没有代码可移植。** 整个仓库就是约 80 个 markdown（规则 + 技能 + 模板）加两个无关紧要的脚本，执行引擎本来就是 LLM 本身。换引擎 = 换一个"读这些文件并照做的 agent"。
2. **状态全部外置。** "文件即真相"是 kit 的第一原则——策略（ONCALL.md）、能力映射（STACK.md）、经验（lessons.md）、审计（paging-log.md）全在 git 文件里，跨会话、可审查。没有数据库、没有 session 依赖、没有专有记忆格式。
3. **工具绑定集中在一处。** 技能只引用 8 个抽象能力槽位（metrics/logs/pager/code/alert-channels/incidents/deploys/flags），厂商名只允许出现在 STACK.md。换工具、换引擎，都只动映射不动技能。
4. **行为约束就是 prompt。** CLAUDE.md 规则 + SKILL.md 流程是自然语言指令，任何模型、任何框架都能消费。

## 2. 引擎需要提供什么

| kit 依赖的能力 | 原版对应物（Claude 生态） | 通用引擎要提供 |
|---|---|---|
| 常驻频道收发 | Claude Tag（Slack 里的 @Claude） | 频道事件订阅（Slack Events API / 钉钉 Stream / HTTP 回调）+ webhook 回发 |
| 定时任务 | Routines（频道内注册） | 调度器（cron / 平台任务）。`templates/routines.md` 是现成的触发器规格书 |
| 只读工具访问 | MCP Connections | 引擎的 MCP 客户端，或按 8 槽位自注册等价工具 |
| 技能按需加载 | Claude 的 skill 机制 | system prompt 注入 + 意图路由（症状 → 加载对应 SKILL.md） |
| 跨会话记忆 | Channel memory | **不需要**——kit 把记忆当缓存，git 文件才是真相，这项直接省掉 |
| 报告页 | Slack Canvas | 任何可链接页面（内部 wiki / 仓库内文件） |

评估任何框架能不能跑 kit，就用这张表逐项打勾——四项依赖满足即可，记忆能力反而是多余的。

## 3. 两条路径

### 3.1 本地 Claude Code：零适配验证路径

markdown 资产零改动（Claude Code 原生以 CLAUDE.md/skills 为指令源），MCP 原生支持，安装五阶段的前四个本来就能纯本地跑。运行期只需一段桥接胶水：

```
告警机器人发消息进群（@ 值班 agent）
  → 聊天平台事件推送（Slack Events API / 钉钉 Stream）
  → 桥接服务：唤起 headless 会话（claude -p，工作目录 = kit 仓库）
  → 诊断经 webhook 回发群里
cron 定时调同一入口跑 routine（weather / 晨报）
```

桥接服务只做三件事：收消息、调 headless、回发。换聊天工具只改这一层（钉钉注意：机器人默认只收 @ 它的消息，告警机器人要带 @）。

### 3.2 通用框架：三薄层自建路径

适合要换聊天工具（钉钉/飞书）、换模型、或深度定制的场景。做法见 §5。

## 4. 可直接复用的资产

| 资产 | 复用方式 | 改动量 |
|---|---|---|
| CLAUDE.md 规则集（19 条常设规则） | 整体注入 agent 的 system prompt | 改名级（"Claude" → 接入方 agent 名） |
| 4 个 SKILL.md（setup/triage/handoff/weather） | 作为 agent 指令按需加载 | 改名级 |
| references/ playbook 结构 | 模板照用，内容用自己的事故史重新挖掘 | 全新内容，结构不变 |
| templates/ 五个模板 | 直接用 | 填空 |
| test-fixtures/（48 个虚构事故 + 答案键） | 框架的 E2E 验收基准——先在虚构数据上跑通，再碰真实系统 | 零改动 |
| eval/replay.md 评估协议、五阶段门禁、shadow 退出标准 | 作为流程规范沿用 | 零改动 |
| examples/run1-webshop | 演示"挖掘 → 盲测 → shadow"全链路的现成样例 | 零改动 |

## 5. 需要自建的三个薄层

### 5.1 触发层

把 `templates/routines.md` 当规格书实现六类触发：

- **事件驱动**：告警频道新消息 → 启动 triage 会话（主链路）
- **定时**：每周 handoff、每 10 分钟 weather（内部有节奏闸门早退，别怕触发频繁）
- **按需**：频道里有人 @ 询问状态 → 现场回答，无需常驻

### 5.2 只读工具桥

按 8 个能力槽位注册工具：查指标、搜日志、读 PR/diff、列部署、读 pager 历史、读 flag 变更、读写仓库内指定文件（lessons.md / paging-log.md 等）。

**关键机会：只注册只读工具，等于把"只读不变量"从 prompt 约束升级成工具层强制——比原版更硬。** 文件写入限定为追加日志文件和提 PR 两种形态。

### 5.3 技能装载与路由

- 按 frontmatter 的 description 做意图路由，把命中的 SKILL.md + CLAUDE.md 规则拼进 prompt
- triage 的 page 级并行调查（每个数据源派一个子代理，只给四样输入：症状句、时间窗、绑定行、首查查询；回报固定四格式：CHECKED / FOUND / NOT FOUND / CANNOT ACCESS）映射到框架的多 agent 编排——前提是框架支持并行子代理与固定回报格式
- 事故会话与例行会话分开管理，避免上下文互相污染

## 6. 落地路径

```
1. fork oncall-kit → 变成自己的策略/playbook 仓库
2. 搭 oncall agent：system prompt = CLAUDE.md 规则 + 技能路由
3. 实现 8 个能力槽位的只读工具桥（先接一两个最常用的源）
4. 用 test-fixtures 跑通全流程 —— 虚构数据，零风险，对照 ANSWER-KEY 打分
5. 按 oncall-setup 五阶段对自己的真实事故史做挖掘，每阶段人工签核
6. shadow 模式上线：诊断发审查频道，人照常值班，每日打分
7. 连续 10 个诊断被判定有用 → 转正
```

第 4 步是关键闸门：test-fixtures 是现成的验收基准，框架能不能忠实执行这套纪律（门禁、防注入、来源标注、盲测），在这里见分晓，不用碰任何真实系统。Claude Code 路径可从第 4 步直接开始——前四个安装阶段纯本地即可完成。

## 7. 风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| 模型指令遵循能力 | 大量纪律是行为性的：通知门命中必发、歧义偏向分页、"修 playbook 不修答案"。这些不考验推理，考验听话 | 换模型前用 test-fixtures 全量验证；不过关就换模型或强化 prompt，不降标准 |
| 术语适配 | 文档里 MCP、canvas、channel memory 等 Claude 生态措辞 | 按接入方术语统一改写一遍 |
| 防注入强度 | 原版防注入主要靠 prompt 纪律 | 可叠加框架层的输入过滤和工具白名单，test-fixtures 里的 INC-2022 注入考点专项验证 |
| 频道集成成本 | Claude Tag 开箱即用，自建要接事件 API、处理线程、渲染 | 若框架已有频道集成则主要是对齐"事故记录 = 频道线程"的约定 |

## 8. 总结

oncall-kit 真正的价值不是代码（它没有），而是**一套被生产环境验证过的值班智能体方法论**：只读分工、门禁安装、经验晋升、盲测退出、全量审计。这套方法论以 markdown 形式存在，天然引擎无关。接入不是移植一个系统，而是给引擎接上三个薄层（触发、工具、技能装载），然后让它读这套文件、照做。选哪条路径取决于：要不要换聊天工具、要不要换模型、愿意自建几层——Claude Code 验证最快，通用框架定制上限最高。
