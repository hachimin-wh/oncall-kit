## 研究对象

**oncall-kit**（https://github.com/anthropics/oncall-kit）是 Anthropic 开源的 AI 值班智能体方案：把 Claude 放进团队的 Slack 事故频道，告警触发后自动调查、给出带证据链接的诊断和修复建议；人做决定并执行，Claude 盯指标恢复、记录经验，下次事故起点更聪明。

三个需要先知道的事实：

- **没有运行时代码。** 整个仓库约 80 个 markdown（规则、技能、模板）加两个脚本（一个 20 行的首次运行钩子、一个测试数据生成器），执行引擎就是 Claude 本身。
- **Claude 全程只读。** 只调查、只提议、只汇报，永远不改被监控系统的任何状态；关闭事故永远是人的动作。这是写死在规则里的，没有例外开关。
- **Playbook 不用从零写。** 安装流程读取团队过去 30–90 天的真实事故历史，自动起草排查手册，人审核后生效。

定位是**参考实现**（Apache-2.0）：fork 走、按自己团队改、随事故沉淀生长，不接收上游贡献。

## 背景

方案出自 Anthropic 官方博客《Claude on call》（2026-08-18），讲的是 Anthropic 内部 CI/CD 团队的生产实践。博客开头的案例：晚上 10 点，新服务 44 个测试没触发，同事只是在频道里 @ 了一下 Claude。Claude 定位出是早上一个 feature flag 引起的，建议回滚；人回滚后 3 分钟，Claude 确认错误率恢复基线——全程没人被叫醒。

注意一个差异：博客描述的**内部版**包含部分门控自动化（自动调金丝雀流量、K8s 节点排水等）；**开源 kit 收敛为纯只读 + 提议**——金丝雀操作变成"给人执行的 ramp 计划"。评估复用时以开源版边界为准。

博客披露的效果数据：

| 指标 | 数值 |
|---|---|
| 首份态势报告（SITREP） | 通常 15 分钟内 |
| 首份基于证据的分析（中位） | 事故开启后 14 分钟 |
| 最快点名根因 | 首份报告内 4 分钟 |
| 某类故障的调查技能文件 | 617 行（与 Claude 排查真实事故后逐轮生成） |
| 整套系统搭建 | 数小时，而非数天 |

两个来自博客的判断：**AI 不会告警疲劳**（人被迫只盯最响的告警，AI 能同时盯所有信号）；质量底线不因自动化放松（每个 PR 有具名负责人、审批后合并、走同一套 CI 门禁）。

## 质量与安全保障

**质量分三层量。** 单次事故：每个论断带证据链接、人类交叉质询、一小时内指标回不回基线。Playbook 级：留出的事故盲测通过率，playbook 大改后重跑。系统级每周三条：值班健康度（事故/page 周环比、误报）、**橡皮图章率**（人类没点开任何证据链接就直接照诊断执行的比例——团队停止质疑的最早预警）、**"坏变更逃逸"计数器**（检验更快的分诊是否真的在保护系统）。

**信任机制。** 五阶段安装门禁、shadow 期证据退出（连续 10 个诊断被判定有用才转正）、weather 八门穷尽清单、每个分页决定全量审计（`paging-log.md`）、仓库不可达时降级模式必须声明。防注入见研究报告的 triage 模块和 test-fixtures 模块——子代理只拿四样输入，被污染的线程带不偏它。
